# Lessons

<!--
HOW TO USE THIS FILE

Newest first, live only. A lesson is a rule that changes future behaviour; if it would not
change what you do next time, do not write it.

- Write one after every correction from the user, without exception. Also after a wrong path
  you had to back out of, after something that worked notably better than the obvious
  approach, and after discovering an undocumented constraint.
- Check for a near-duplicate first. If one exists, MERGE into it and sharpen its mitigation
  rather than adding a second entry.
- Supersede, never overwrite. Write the new entry first, then MOVE the old entry into
  docs/lessons-archive.md, creating that file if it does not exist, with one line prepended:
  "Superseded YYYY-MM-DD by: <new entry title>". A lesson that no longer applies moves the
  same way. Never delete an entry; move it.
- When a lesson has hardened into a standing rule, add a one-line entry for it in the
  project's AGENTS.md as well.
- Read this file in full before the first edit of a session and say which entry applies, or
  "no recorded lesson applies".
- The title is an instruction, not a topic. The mitigation must name when to act and what
  to do, scoped to the evidence: a one-off preference is not a universal rule.

Entry format:

### <short imperative title>: YYYY-MM-DD
- **Context:** <the situation, one line>
- **What failed:** <what went wrong, or "n/a">
- **What worked:** <what actually helped>
- **Mitigation:** <the rule to follow next time: must be actionable>
- **Tags:** <comma, separated, tags>
-->

### Agree the frame before synthesising: 2026-07-28
